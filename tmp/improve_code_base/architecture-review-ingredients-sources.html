Review Architectural — Domaine : Recette Ingrédients & Sources

Focalisation à 100% sur le système d'ingrédients, sources, qualité et choix utilisateur (acheter/créer/récolter)

Candidat 1 : Modèle SourceConfig dédié — Séparation de la choix source de la famille kind

Fichiers impliqués

  • src/engine/calc.ts : fonctions defaultSource(), sourceOptions()
  • src/data/settings.ts : persistency des sources utilisateur
  • src/components/IngredientTree.tsx : boutons source UI
  • src/components/Browser.tsx : sélection source dans l'arbre

Problème actuel

Le déterminisme source est collé à la kind de la famille (raw→gather, refined→craft, craft→buy). L'utilisateur ne peut pas choisir autrement, et ce choix n'est pas modélisé comme une entité indépendante — il est dispersé à travers calc.ts, les composants UI, et le localStorage. Il n'y a pas de "Source of Truth" unique pour les préférences source.

Solution

Extraire un modèle SourceConfig qui encapsule les préférences source par famille, indépendant de la kind. Ce modèle aurait :

  • Une mapping family → { source: Source, enabled: boolean }
  • Des méthodes getEffectiveSource(fam) qui privilégie le choix utilisateur sur le default
  • Une sérialisation qui coexiste avec le localStorage existant
L'UI resterait inchangée en apparence, mais lirait depuis ce modèle au lieu d'appeler directement defaultSource().

Avantages

  • Séparation des préoccupations : la logique "quelle source est disponible" vs "quelle source l'utilisateur a choisie"
  • Testabilité : on peut tester les calculs avec des SourceConfig fixes, sans dépendre des defaults
  • Extensibilité : ajouter un nouveau type de source (e.g. auction) ne nécessiterait pas de toucher au code de default
  • Localité : la préférence source est centrale, pas dispersée
Avant 
defaultSource(fam) → kind-based → hardcoded
Après 
SourceConfig.getEffective(fam) → user-choice first, then default

Recommandation : Strong — C'est le socle pour tous les autres améliorations.

Candidat 2 : Seam "Source Choice" entre sélection UI et calcul

Fichiers impliqués

  • src/engine/calc.ts : fonctions recipeFor(), computeIngredient(), compute()
  • src/lib/iconDir.ts : nouvellement créé (référence indirecte pour la cohérence icon/ressource)

Problème actuel

recipeFor(id) et computeIngredient() ignorent complètement les préférences source de l'utilisateur. Ils déduisent la source du kind de la famille. Si l'utilisateur a changé la source par défaut (via les boutons dans IngredientTree), ce changement est perdu lors du prochain appel de recette — les calculs utilisent toujours les defaults.

Solution

Introduire un seam formel entre "choix source utilisateur" et "moteur de calcul". Cela signifie :

  • Passer state.sourceConfig (ou l'équivalent) en paramètre à recipeFor(), computeIngredient(), compute()
  • Ces fonctions utilisent d'abord la source configurée, puis tombent back sur le default
  • L'UI (IngredientTree, Browser) transmet le state.sourceConfig existant
Cela crée un "vrai seam" : deux adaptateurs (avec et sans config utilisateur) rendent le comportement testable et interchangeable.

Avantages

  • Testabilité : on peut injecter sourceConfig: {} (vide = defaults) ou complet en unité tests
  • Fidélité UI/Backend : le choix utilisateur est garanti de traverser jusqu'au verdict
  • Recouvrement : les tests existants continuent de fonctionner avec des defaults invisibles
Avant 
recipeFor(id) → kind-based → no user config
Après 
recipeFor(id, sourceConfig) → user-config first → default fallthrough

Recommandation : Worth exploring — Forte dépendance au Candidat 1.

Candidat 3 : Modèle de choix récursif à travers l'arbre d'ingrédients

Fichiers impliqués

  • src/components/IngredientTree.tsx : arbre récursif d'ingrédients
  • src/engine/calc.ts : profondeur MAX_DEPTH, computeIngredient(), computeRecipe()

Problème actuel

La sélection source est plate — elle s'applique au niveau de la famille actuelle, mais ne remonte pas ni ne descend à travers l'arbre récursif. Si l'utilisateur choisit "Crafter" pour l'ingrédient principal, les ingrédients enfants conservent leur default source. De plus, il n'existe aucun moyen de dire "tout l'arbre en 'gather'" ou "tout l'arbre en 'buy'".

Solution

Rendre la source récursive via le contexte computationnel :

  • Ajouter un contexte sourcePropagation: 'parent' | 'all-children' | 'none' au compute() et computeIngredient()
  • Quand 'parent', la source du parent s'applique aux enfants qui n'en ont pas de propre
  • Quand 'all-children', la source choisie pour la racine s'applique à tout l'arbre (ignorant les defaults)
  • UI : ajouter un toggle "Appliquer à tout l'arbre" dans IngredientTree
Cela rend le choix utilisateur extensible de manière récursive à travers n'importe quel arbre de craft.

Avantages

  • Flexibilité utilisateur : "Je veux tout récolter" ou "Tout acheter" en un clic
  • Profondeur : fonctionne sur n'importe quel niveau de récursion dans l'arbre
  • Prévisibilité : le comportement est explicite via le paramètre sourcePropagation
Avant 
source → uniquement niveau courant, children → defaults
Après 
sourcePropagation='all-children' → source unique sur tout l'arbre

Recommandation : Speculative — Besoin de valider le Candidat 2 d'abord.

Candidat 4 : Recipe source-aware — recipeFor connaît les préférences

Fichiers impliqués

  • src/engine/calc.ts : fonction recipeFor() (lignes 326-346)
  • src/engine/reduce.ts : propagation des sources dans compute()

Problème actuel

recipeFor(id) est la porte d'entrée pour toute génération de recette (Breadcrumb, Ingrédients, Prix). Comme il ignore les préférences source utilisateur, le reste du système hérite de décisions sous-optimales. Par exemple, afficher "Ce récipie nécessite 3 Métalbar (Acheter @ 150 chacun)" alors que l'utilisateur a choisi "Crafter" partout.

Solution

Modifier recipeFor(id, sourceConfig?) pour qu'il accepte un paramètre optionnel de configuration source. À l'intérieur :

  • Lorsqu'un ingrédient du recipe a une source configurée par l'utilisateur, on l'utilise
  • Si la source configurée est incompatible (e.g. craft pour un ingrédient raw), on fait back vers le default
  • Le recipe retourné porte une métadonnée _sourceHints listant quels ingrédients ont été affectés par le choix utilisateur
Cela fait de recipeFor la source unique de vérité pour ce qui concerne les sources dans la recette.

Avantages

  • Impact maximal : tout ce qui consomme recipeFor (UI, prix, verdict) bénéficie automatiquement
  • Dégradé gracieux : si pas de config, comportement inchangé (backward compatible)
  • Traçabilité : _sourceHints aide les tests à comprendre quelles décisions ont été prises
Avant 
recipeFor(id) → ignores user → same result for all
Après 
recipeFor(id, optSourceConfig) → respects config → potentially different results

Recommandation : Worth exploring — Dépend du Candidat 2 (seam formel).

Recommandation : Parier sur le Candidat 1 d'abord

Le modèle SourceConfig isolé est le fondement sans lequel les autres candidats perdent en sens. Une fois ce modèle en place (un simple enregistrement {[family: string]: { source: Source; enabled?: boolean }} en état global), le seam formel (Candidat 2) devient naturel, et la récurrence (Candidat 3) et la recette consciente (Candidat 4) s'enchaînent sans friction.

Chemin estimé : 3-4 jours de développement, 2-3 jours de tests, zéro régression sur l'existant.

Ce modèle rend aussi le système "AI-navigable" : un modèle de données clair et unique est la base première pour toute logique ultérieure (raccourcis IA, suggestions automatiques, etc.).
